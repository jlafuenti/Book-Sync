# Who owns the request transaction

`server/database.py`'s `get_db()` yields a session, commits it after the handler returns, and rolls
it back if the handler raised. That is the whole contract: **one request, one transaction, one
commit, and the dependency owns it.**

`routers/library.py` also calls `await db.commit()` by hand around twenty times. Reading a handler
did not tell you whether a given call was doing something the request depended on or repeating what
`get_db` was about to do anyway — and a helper extracted out of one handler carries its `commit()`
with it, silently changing the atomicity of every new caller. `services/position_service.py` had to
spell the rule out for itself to avoid exactly that; this is the same rule for everyone else
(issue #259).

## The three conventions

| Where the code runs | Who opens the session | Who commits |
|---|---|---|
| A request handler | `Depends(get_db)` | `get_db`, at teardown |
| Background work (queue manager, schedulers, the library scanner) | itself, `async with async_session()` | itself, and its docstring says so |
| A helper called by either | nobody — it takes a session as an argument | nobody |

The third row is the one that goes wrong quietly. **A helper never commits.** It may `flush()` — to
get an autogenerated id, or to make a row visible to a query later in the same transaction — because
a flush stays inside whatever transaction the caller is running. It may open a `begin_nested()`
savepoint. It may not decide, on its caller's behalf, that the work so far is durable. If a helper
genuinely must commit, it is not a helper: give it a name that says it owns a transaction and a
docstring that says why.

## When a handler may commit anyway

Two cases, and both must carry a one-line comment saying which one it is.

**1. Persist before an external side effect.** The handler is about to do something outside the
database that can fail or cannot be undone — rewrite an EPUB's OPF, write m4b tags, unlink a file.
Committing first bounds the damage to the harmless direction: the library knows something the
filesystem does not yet, rather than a file that has been rewritten or deleted for a change the
database rolled back.

In `routers/library.py` today: `resolve_metadata_discrepancy` (before the metadata write-back),
`delete_ebook` and `delete_audiobook` (before the unlink), and the two Audiobookshelf enrichment
endpoints, whose advertised answer is "updated in the library, but the file's tags could not be
written" — so the row change has to stand whatever the tag write reported.

These are pinned by `server/tests/test_request_transactions.py`, which exists so the clean-up
invited below cannot delete one by accident. Each test says what it would catch, including the one
that would not catch anything today and why it is still worth having.

**2. Progress inside a long job.** A scan, a rehash, a normalize pass — anything that walks the
whole library. One request-long transaction means a crash discards every row the job touched, and
Postgres holds a write transaction open for the length of the walk. So these commit in batches, via
the `_Batch` helper in `routers/library.py` (`SCAN_COMMIT_BATCH`, issue #202): `tick()` once per
item, commit every 50. The final short batch is committed explicitly too — `get_db` would do it for
a request, but these jobs also run from the import scheduler, which has no request around them.

This is a deliberate exception to "one request, one transaction", not an oversight: the batch size
is chosen for the crash window, and partial progress is the point. Do not collapse it back into a
single commit.

## The rest

Every other `await db.commit()` in a handler is a trailing commit that duplicates `get_db`'s. They
are harmless, and they are on their way out — **opportunistically, a few per PR as each endpoint is
touched, never as a bulk sweep.** Some of what looks trailing is not: a commit can be followed by
code that re-reads the row through a *different* session (a write-back helper that opens its own),
and only that endpoint's own test will tell you. So each removal ships with a run of the tests that
already cover that endpoint — `test_library_lists.py`, `test_uploads.py`, `test_enrich_abs_router.py`,
`test_match.py`, `test_narrator_metadata.py`.

## Checklist for a new handler

- Don't commit. Let `get_db` do it.
- Committing anyway? Say which of the two cases it is, in a comment, on the line above.
- Extracting a helper? Strip the `commit()` out of it and leave it in the handler.
- Writing background work? Open your own session and say so in the docstring.
